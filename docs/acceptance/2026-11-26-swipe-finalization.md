# 1.0.5-fix.2 流式 swipe 与保存收尾复核

日期：2026-11-26。基准为前端分支 `codex/1.0.5-indexeddb-recovery` 的 `39e7aae`；本轮版本仍为 1.0.5-fix.2。

## 结论与复现条件

用户要求的正常回复 → 新 swipe → 等待原生保存 → pending 归零及 saved → 左右切换已有候选流程，最初在两个酒馆版本及两种备份位置均通过。随后按用户补充，重点测试最近楼层备份、完整备份与流式生成同时开启。

确认了一个额外触发条件：新 swipe 仍在生成时刷新备份。修复前，原生酒馆 1.19.0、Edge、真实 IndexedDB 中，第一条回复正常回绿；新候选生成途中调用现有手动刷新入口，生成完成并实际保存后仍留下 2 行 pending（操作根及消息副本），状态为 `unconfirmed`。实际 JSONL 与完整页面消息的原生哈希相同，但剩余记录不能沿原证明链被确认。不是文件没有保存，也不是只剩界面颜色没有刷新。

基准失败现场：`.local-test/yellow-fix-20261125/1.19.0-08a708b9-8c20-4ad5-93fd-e151adaf5c39/trace.jsonl`；另行读取该目录实际 JSONL，核对页面哈希相等、pending 2、可确认记录 0。

用户随后确认：生成期间曾将网页切到后台一次再返回，提示为“正在核对第二层是否保存”“第二层保存待确认”。这些触发条件和表现与复现吻合。仍未读取其原始 pending，不能据此直接追认或清除旧记录；未清除或修改用户的真实聊天与备份。

## 四个环节的衔接

1. `MESSAGE_SWIPED` 在新候选尚未建立时会带着超出 `swipes` 的临时选择。即时捕获跳过该占位事件是原有设计，不应伪造已完成候选。
2. `createPendingObserver` 保留事件发生时的不可变消息副本。生成期间，批处理及核验前的 `settle()` 可以追加中间状态、生成时长、候选信息等后补字段；不会重写先前记录。
3. 原协调器只有事件批次附带 capture 时才做收尾观察。手动刷新、页面恢复等没有 capture 的调用会直接重置观察器；流式内容若在两次观察间变化，这次重置会漏掉一段状态转换，使旧操作与最终状态断开。
4. `confirmedJournalRecords()` 继续要求实际文件终态、整聊与逐消息哈希、可反推的前态及操作连接关系。链断开时它保留旧记录是正确行为，不应靠忽略候选或清空 pending 绕过。

## 实际修复

仅修改前端协调器：存在当前待确认 journal、尚未落库的捕获或本批事件捕获时，刷新先追加 `settle()` 结果并持久化，继续原观察链。没有待确认操作时，继续使用原初始化/重置流程，不把未知的静默缩短补记为用户删除。

事件捕获、observer、`settle()`、`confirmedJournalRecords()`、条件核销及备份证明算法均未改动。后端、数据库版本 9、协议、pending 格式和备份策略不变。本轮不追认已经断开的旧链，不自动清除用户已有黄灯记录。

## 验证方法

复用隔离原生酒馆入口 `tests/browser/run-native-finalization-contract.mjs`，增加 swipe 场景。每次使用独立 dataRoot、JSONL、浏览器上下文和 SQLite 目录。测试调用原生 `Generate('normal')`，点击原生右候选按钮生成新候选，再点击左右按钮切换已有候选。

只有模型响应边界使用本机 HTTP 合成提供器；不请求外部模型。流式响应分段发送，每段间隔 1200ms，经过酒馆原有 SSE、StreamingProcessor、事件、渲染及保存流程。页面恢复测试派发 `pagehide/pageshow` 调用真实生命周期处理器，不等同于移动系统挂起真机测试。

`swipe-ui-*` 场景直接启用实际扩展及其默认 500ms 事件批处理、自动核验和重试；不在保存后用手动核验强行促成通过。核验延迟设为允许的 500ms，以覆盖原生延迟保存尚未完成时的自动重试。两种备份位置均使用真实存储层。

WebKit 的连续场景记录中观察到：一次 pending 为空及 saved 的读取，可以早于下一批捕获落库；紧随其后的最近备份读取仍是上一阶段，pending 随后已经新增。因此自动验收不以一次状态读取退出，而是在 45 秒上限内要求连续两次文件、两份备份、pending 和终态一致。该现象与本轮确认的永久断链区分记录；本轮没有修改一般瞬时绿灯发布机制，也不以短暂绿灯证明自动收尾成功。

每个场景检查：第一条回复、新候选、切回旧候选、再切回新候选后，pending 为 0、状态 code 和可见状态节点均为 `saved`；页面完整 JSON 与实际 JSONL 一致；最近备份和开启时的完整备份均与完整原生消息相符，包含两条候选及其信息。切换已有候选不能额外请求生成。

- 全量单元测试：471/471。新增同步/异步哈希下候选补记和核销、生成中手动/生命周期刷新的操作链接续、无 pending 时未知缩短仍冻结完整备份的回归。
- Edge / 酒馆 1.19.0：两种备份位置的生成中刷新、页面恢复均归零并回绿；未保存删除/编辑、旧文件回载继续保留可恢复 pending，18 行旧积压接续新活动后正常核销，共 10 个组合通过。结果：`.local-test/yellow-fix-20261125/1.19.0-3a129429-5456-44af-a4d6-c1f3b8b4628f/results.json`。
- Edge / 酒馆 1.15.0：两种备份位置的生成中刷新、页面恢复，共 4 个组合通过。结果：`.local-test/yellow-fix-20261125/1.15.0-590ddc2d-8e14-4248-8a33-cb251a032d13/results.json`。
- WebKit / 酒馆 1.19.0：两种备份位置的生成中刷新、页面恢复，共 4 个组合通过；生成响应恰好 8 次，切换已有候选不新增请求，无 pageerror。结果：`.local-test/yellow-fix-20261125/1.19.0-c3867b49-97dd-4787-8510-f413c2742756/results.json`。最终截图已检查，可见绿色“酒馆聊天已保存”和候选 2/2。
- WebKit / 酒馆 1.15.0：两种备份位置的生成中刷新、页面恢复，共 4 个组合通过，生成响应恰好 8 次，无 pageerror。结果：`.local-test/yellow-fix-20261125/1.15.0-50733f7f-cb56-478b-8c53-21b4d2d9ff3c/results.json`。
- 上述最终矩阵合计 22 个组合；其中 16 个为完整备份开启时的流式 swipe 刷新/恢复路径，另 6 个为未保存保护及旧积压接续。全部正常路径 pending 为 0、终态 saved；保护路径保留 pending 并可生成正确恢复目标。
- 未执行：外部真实模型、用户原库、Termux/iOS Safari 真机及操作系统实际挂起；本轮未重跑无关的 120 秒事务压力、后端全量测试或发布流程。

初期夹具保存等待、重试配置及流式观察窗口调整前的失败现场保留，不计为产品缺陷或通过证据；产品缺陷以上述原生失败现场及单元回归为依据。
