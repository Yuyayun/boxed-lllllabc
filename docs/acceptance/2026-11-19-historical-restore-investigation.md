# user 旧楼层修改后恢复成旧正文：定位与复现

日期：2026-11-19。本文保留修复前的调查结果；当时只调查、补充诊断测试。后续已完成本地修复，最新状态见[修复验收](2026-11-19-backup-race-fix.md)。诊断脚本现已转为要求恢复新正文的安全回归测试，下文 10 个场景及 `probe.log` 为修复前证据。

## 结论

已在独立内存 SQLite 中复现“旧 user 楼层已修改，随后状态变绿、pending 清空、完整备份继续更新，但整聊恢复仍得到修改前正文”。第 1116 层与现场提到的第 26 层均已复现。

正常编辑的对照测试没有发现 user 消息被特殊遗漏：第 26、1116 层都能进入 historical/full，确认保存后清除 pending，两类恢复都得到新正文。

问题在于一次修改的备份未完成后，没有可靠地把这次欠下的修改接续到下一轮。revision 冲突是一种触发条件；正常新消息到来造成来源变化，也能触发同类结果。因此，仅降低 revision 冲突不足以解决历史修改遗漏。

这证明当前代码能够产生与用户反馈相同的结果；尚无用户当时的逐步记录，不能认定现场一定经过下面某一条时序。

## 已确认的触发链

### 1. 正常新消息到来，就可以暴露遗漏

1. 先建立 1136 层完整备份和正常的 full view 缓存。
2. 编辑旧 user 楼层。pending、historical、recent 依次成功写入。
3. 完整备份准备写入时，新消息到来，记录来源变化并将新消息事件排到下一轮。
4. 本轮 full 的来源保护正确拒绝写入，返回 `backup-source-changed`，旧正式副本保留。
5. 下一轮只收到新消息事件。完整备份仍把原来的缓存视为可信，只更新新楼层，没有补写上一轮失败的旧楼层。
6. 核对器确认酒馆文件里已经有新正文，清除 pending，状态变成 `saved`。
7. full 已增加到 1137 层，但目标旧楼层仍为修改前正文；用真实整聊恢复执行器恢复，得到的也是旧正文。

该场景没有制造 revision 冲突，也没有伪造存储失败。第 1116、26 层各跑一例。historical 在这两例中保留了新正文，因此逐层历史恢复仍可得到新正文。

### 2. 手动核对与 full 更新交错

在旧楼层 pending/historical 写好、full 更新尚未执行时，插入一次真实 verifier 调用，模拟点击“检查保存状态”：

- verifier 确认酒馆文件已保存，删除 pending、更新 meta；
- full 请求仍持旧 revision，真实 SQLite 校验返回 `backup-conflict`；
- 后续新消息走增量路径，漏掉先前失败的旧楼层；
- 最终变绿、pending=0、full=1137 层，整聊恢复仍是旧正文；historical 恢复为新正文。

普通备份开始前已有取消核对保护，不能把此例写成“每次自动 2 秒核对都会打断同页普通备份”。这里测试的是备份开始后新发起的手动核对；其他页签的写入也不能由本页取消覆盖。

### 3. historical 自己失败，也不会自动补写

先保留目标层之前的一条历史备份。在 historical 的 summary 与 patch 之间执行一次真实的无关 meta 写入，让 revision 校验拒绝历史更新：

- 本轮 full 可以成功，historical 仍旧，pending 保留新正文；
- 下一条新消息不会重新发出旧楼层编辑事件，也不会补写旧 historical；
- 后续核对清除 pending，状态变绿；
- 此时整聊恢复为新正文，但该层历史恢复为旧正文。

额外测试让 historical/full 各发生一次真实 revision 冲突：后续新消息成功并变绿后，两份副本都仍是旧正文，pending 已清空。该例需要两次可控交错，证明保护接续的缺口，不代表所有现场都会同时失败。

## 代码上的接续缺口

1. `src/backup/full-bounded.js` 的增量可信条件只核对缓存的层数与 `fullBackupAt`。失败保留了旧正式备份，这两个值也就仍与旧缓存匹配。失败的编辑事件没有因此重新进入下轮目标集合。
2. `src/controllers/backup-coordinator.js` 的 full 失败路径没有使该聊天的 full view 失效；失败事件没有形成后续必须补写的记录。下一轮另一个事件全部成功，便清除该聊天的 `backupProblems`。
3. historical 仅由当前触发事件生成记录。历史写入失败后，后续普通新消息既不会重新捕获那个旧层，也不会从 pending 补回失败的历史内容。
4. `src/controllers/backend-verifier.js` 的 pending 核销依据是酒馆文件内容确认及记录未被更新。它没有同时证明这条改动已接续到应有的长期备份；full 是否需要额外确认主要由 meta 的 awaiting/frozen 标记判断。普通 patch 失败仍可能留下 active 状态。
5. `createFullRestorePlan()` 按 full 构造目标聊天，pending 用于冲突提示与验证，不作为正文覆盖层；它也不自动合并 historical。历史逐层恢复则只使用 historical。这解释了同一层在两种恢复入口中可能出现不同内容。

第 5 点是当前恢复来源的明确选择规则，不能简单通过“恢复时把历史记录都覆盖进去”修补，否则可能破坏完整副本的一致性及保留旧副本的语义。应优先修复备份接续。

## 补充：用户原话与“黄灯后确认保存报错”

同日收到的反馈原话要点：浏览器存储时“发一句就保存一句”、绿灯；改用服务器存储后出现黄灯待确认，点进去想确认保存时出 bug，因此感觉新数据无法录入。用户随后补充：同一条反馈还包括“26 层是修改过的 input，档丢了再救回来，恢复的是 26 层没有修改时的 input”。这里 input 指 user 消息正文，不是扩展附加字段。

两句话需要作为同一条反馈理解：前半段描述保存确认异常，后半段报告救档确实返回旧正文。因此，应把“最新修改没有进入最终恢复结果”作为实际反馈，不能仅以黄灯或错误显示解释整件事。这与本报告第 26 层的漏补复现吻合，但仍不能据此唯一锁定触发时序：尚不清楚其点击的是“检查保存状态”、进入“请求酒馆保存”，还是在确认窗口里点击“确认重新保存”，也不清楚救档选择了整聊还是历史逐层来源。

本次增加两个真实 SQLite 场景，最新一条均为 `is_user: true`：

1. **新消息已经备份，核对前仍黄灯。** 追加第 1136 层后，recent、full、pending 三处均读回新正文，状态为 `checking`；执行已经安排的自动核对后，pending 清空、状态变成 `saved`。因此，核对期间的黄灯本身不能证明服务器备份未录入。
2. **进入请求保存时，自动核对恰好更新 pending，导致入口报错。** 新消息写入后保持黄灯，调用真实 `createRestoreUiState().onRequestSave()`；在该入口读完 summary、读取第一张 pending 页之前，执行此前安排的自动核对。自动核对确认合成酒馆文件已保存，删除 pending 并更新 meta；入口后续分页使用旧 revision，被真实 SQLite 拒绝，返回 `backup-conflict` 并把全局状态设为 `backup-read-failed`。这时 full 中仍能读回新 user 正文，pending=0，重新请求原生保存的调用次数为 0——报错发生在读取准备阶段。

第二例对照了生产回调，并使用可控计时器触发已安排的自动核对，不伪造错误；没有执行真实网页点击和原生酒馆文件读写。它证明“黄灯 → 进入确认保存 → 报错”可以发生在新数据已经写入的情况下，仅解释该反馈的前半段，不能用来否定后半段的旧正文恢复结果。后半段已由前面的第 26 层漏补测试给出可重复的同类实现路径；尚不能认定现场必然采用了这一时序。

后续应分别验证“新数据备份是否成功”“酒馆保存是否确认”“确认入口读写是否冲突”及“失败旧修改能否接续恢复”，不能将它们都显示或解释为没有保存。

## 对修复范围的建议

- 保留 revision、来源变化拒绝、原子发布等保护；失败时应记录和补写未完成的楼层，而不是仅在下一轮处理新事件。
- full 一次更新失败后，至少要使后续增量快路失效，直到重新核对完成，不能仅凭旧层数和旧时间戳继续信任缓存。
- historical 的失败修改也需要接续，不能只修 full。临时队列、页面重载后的恢复及结果未知时的处理需要一起设计。
- pending 的核销应与已启用备份类型的未完成补写协调，防止最后一份包含新正文的箱装记录在补写前被删除。
- 状态不能因下一条无关新消息备份成功，就忘掉旧楼层尚未完成的备份；应在补写验证后清除对应故障。
- revision 粒度与读取重试仍需按原排查说明修复，但这两项不能代替上述接续保护。
