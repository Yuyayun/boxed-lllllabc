# 1.0.5-fix.1 旧数据连续恢复补修

日期：2026-11-25。分支：`codex/1.0.5-legacy-recovery`。版本后缀由用户确认为 `1.0.5-fix.1`；本次为开发分支补修，尚未合并或正式发布。main 保持已发布的 1.0.5；修复分支推送不代表正式发布。

## 源码核对与实现选择

原 `pending-recovery.js` 确实按旧楼层号收集不同正文，再计算逐层候选数量乘积；超过 64 就停止。删楼后的整段位移会被误当成大量独立冲突。旧记录又没有可靠的分支组号，不能简单按时间选最新一层，或把限制调大。

本次将纯旧数据恢复移入 `legacy-recovery.js`：

- 保留当前聊天、完整备份、最近备份及旧 numeric 的连续顺序。历史副本保留记录时间和来源，共同时间的连续历史片段作为整体使用；孤立副本只补有唯一正文的缺口。
- 以完整原生消息内容建立序列锚点，旧楼层号只作位置线索。替换、平移和拼接以完整连续片段处理，未再逐楼层自由排列组合。
- 对“新片段已经表明整体前移，但删除发生在片段之前”的情况，检验完整的连续删除历史。利用旧校验算法的正向与逆向运行状态，线性过滤删除边界，再用既有 `hashCanonicalChat` 复核整个结果；只使用已有正文，不从校验值生成消息。
- 先确认旧 structural 所指的整聊状态，再接续其后的明确 numeric 记录。最近或完整备份中的连续后续内容也参与恢复；没有后续保护记录可佐证时，保留完整状态让用户选择，避免仅凭一次较新的备份时间把已删除旧尾巴重新插回。
- 同时存在完整的不同分支时，按整条分支选择，不依据时间戳单独选一条，不产生交叉消息、不使用 swipe 承载另一聊天、不另建聊天。

还修正了一个读取入口问题：旧 structural 即使刚好能与当前聊天匹配，也必须读取最近、完整及历史副本再判断，避免未加载的副本中实际存在另一套完整内容。纯新版操作日志仍走原路径，不进入旧分支选择逻辑。

## 选择与保存

可唯一确认时，直接进入原来的“恢复未保存变更”预览。需选择时，界面展示分叉位置、每套连续内容及共同前后文；消息可分页展开，正文相同但附加内容不同时也可查看其他已保存字段。选择只打开普通预览，不写数据库。

选择期间检查聊天、文件身份、待确认记录和备份位置；确认恢复前继续复核参与恢复的备份来源。取消、关闭或在读取期间退出均不写入、不恢复。未选择的计划不能执行。

应用仍使用原有恢复执行器：先追加恢复保护，保留所有旧记录，再修改聊天、请求保存并按原流程重读核对。未选分支不进入恢复后的聊天；原始备份及旧记录不会因预览或选择就被删除。

## 兼容与边界

本节所述旧恢复逻辑可继续配合服务器插件 1.0.5 使用。后续同后缀补修还包含[运行日志修补](2026-11-25-runtime-log-fix.md)，该部分需配套服务器插件 1.0.5-fix.1；旧后端会跳过新增诊断请求，不影响恢复。IndexedDB 9、SQLite schema 4、protocol 6、操作保护记录格式和存储保护能力均不变；没有清库、迁移或放宽容量限制。上表为旧恢复阶段的验证记录，后续日志补修后的完整回归见日志验收。

旧记录若真实缺正文，或者剩余片段无法建立可验证的连续关系，仍停止自动恢复并保留记录。多个完整分支进入选择；不能把零散、无法确认顺序的正文包装成可选的假分支。本次自动化使用合成夹具，未验证用户现场原库及 Termux/Safari 实机。
