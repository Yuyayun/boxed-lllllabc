# 备份竞态与旧楼层修改漏补：修复验收

修复日期：2026-11-19；版本整理：2026-11-20。当前版本为 1.0.3，保存在前后端同名开发分支 `codex/1.0.3-backup-race`，尚未发布。原始调查见[修复前复现记录](2026-11-19-historical-restore-investigation.md)。

## 最终行为

- 第 26、1116 层 user 正文从 A 改为 B，备份被新消息打断后，后续会接续 B；完整和历史逐层恢复都得到 B。
- 历史和完整更新均失败时，保护记录保留。刷新控制器或重启 SQLite 后，可依据持久记录补写。
- 酒馆文件确认已保存，并不足以提前清除尚未补入备份的改动；持续补写失败时不会因下一条消息或一次核对而变绿。
- 后台清除 pending、更新保存状态，不再让 full 分页或 full 写入因无关的全库 revision 变化而失效。
- 确认保存入口读取时遇到版本变化，会有限重读；确认窗口打开后若只是后台核销部分记录，聊天和剩余记录未变时仍可继续保存。新增/修改待确认内容、聊天内容变化仍要求重新确认。
- 查看/恢复预览/管理入口的读取失败在当前操作显示，不覆盖原来的聊天保存状态。

## 实现边界

### 持久补写与核销

复用现有 `pending_changes`，新增可选 `backupTargets`，记录这条内容应完成的备份类型；没有增加数据库仓库。旧 pending 在备份流程中补充要求后接续。近期消息要求 recent，完整备份开启时要求 full，历史范围内编辑要求 historical。

协调器在新一轮中合并未完成楼层，full 失败时撤销增量缓存的可信状态。历史补写只接续属于历史修改的记录，不把普通新消息额外视为历史编辑。修复重放核对当前楼层哈希，拒绝把旧 B 写回用户后来的 C。

条件核销在同一个数据库事务内重核 pending 指纹、取消状态及对应副本。所需副本仍旧就保留记录，核对器尝试补写后再次核销。读取证明涉及其他仓库，但只推进 pending 的写版本。recent 中已按正常窗口滚出的旧消息按保留范围处理，不要求无限保留最近备份。

聊天结构改动使用完整副本的已提交聊天哈希；普通 full 写入和手动处理冻结副本会撤销旧证明，不能沿用旧哈希。明确删除后追加新消息，只在当前聊天仍与删除时的前缀一致时接续删除，避免误把丢档当主动删除。

### 正文版本与安全重试

保留原全局 revision，供迁移、目录清理和旧客户端继续使用。新增按备份类型区分的正文版本，以及数据区/迁移代次凭据。full 写入另外检查冻结/待确认等保护状态。迁移提交、撤回和旧任务恢复推进数据区代次，切回原区域也不能复用旧读取凭据。

本次粒度是“备份类型”，还不是逐聊天索引；其他聊天对同类正文的写入仍可保守触发冲突。没有引入全局操作队列或取消原有防覆盖规则。

单类读取最多从头尝试 3 次。恢复涉及多类副本时，作为整组重新读取，避免各自重试后混用版本。只有明确的版本变化才重试；稳定版本下的坏记录不隐藏或反复重试。连续变化时返回可重试提示，不返回半份/混合结果。

分批写入仍按提交回执核对。单批响应中断保留结果未知，后续使用实际副本证明判断，已提交内容不为了消除未知状态而再覆盖一次。

### 兼容

- IndexedDB schema 8、SQLite schema 4、存储协议 6 不变；无需清库或重新搬数据。
- 前端及配套后端需共同更新。新后端通过 `pendingBackupProof` 能力声明事务核销保护。
- 新前端连接旧后端时，小操作及读取仍可使用；若旧后端缺少核销保护能力，新前端保留带补写要求的记录并提示更新，不在旧服务上冒险清除。
- 旧前端连接新后端的普通接口继续工作；新字段及类型版本作为可选能力增量提供。
- 后端实现位于本机 `.local-test/boxed-lllllabc-server-dev`。29 个共用模块中 28 个逐字节一致；唯一既存差异仍是日志时间展示的本地时区/服务器 UTC。
